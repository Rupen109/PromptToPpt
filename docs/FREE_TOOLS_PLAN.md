# Free tools — acquisition plan

Goal: bring in search traffic with small free tools whose natural next step is "make this a designed deck in SlidesDone".
Principle: every tool ends in the same call to action — the result (outline, summary, PDF) is carried into the editor through the
existing anonymous **draft** hand-off, so the visitor never starts over.

## How a visitor is carried into the product

`result → POST /api/v1/drafts {prompt, attachmentIds} → editor /start?draft=<id>` (the draft is single use and claimed after sign-up/login).
For PDFs the file is parsed once, kept for one hour as a draft attachment, and handed over, so the editor does not need a second upload.

## Cost protection (these endpoints are public, anonymous and paid by us)

1. **Burst**: 6 requests/minute per IP across the tools.
2. **Per visitor per day**: `FREE_TOOLS_IP_DAY` (default 20) model calls per IP.
3. **All free tools together**: `FREE_TOOLS_USD_DAY` (default **$3** in any rolling 24h, read from the usage ledger, request types `free_*`). Past it the tools answer "busy"; signed-in customers are unaffected.
4. The app-wide AI circuit breaker (`AI_BUDGET_USD_*`) also pauses them.
5. Inputs are small: topic ≤ 300 characters, PDF ≤ 5 MB, ≤ 30k characters sent to the model, output token caps, no thinking budget.
6. The model is told the visitor text is data, never instructions (same wrapper rules as the main product).

Not yet in place (do before real traffic): Cloudflare Turnstile on the tool forms (the server helper exists — `verifyTurnstile`),
a shared rate-limit store when the API runs on more than one instance (the per-IP counters are in memory).

## Measuring it

The owner dashboard (Cloud → Cost per action) has a **Free tools** row: what visitors cost us. Conversion = draft claimed after sign-up ÷ tool runs;
the `drafts` table already records unclaimed vs claimed drafts. Add a `source` column to `prompt_draft` (e.g. `free-tool:outline`) so conversion can be split by tool
before turning on paid acquisition.

## PDF editor (`/free-tools/pdf-editor`)

- Code: `apps/web/lib/pdf-editor/` (model + history, geometry, render (pdf.js), export (pdf-lib), text, images, tools) and `apps/web/components/free-tools/pdf-editor/`. pdf.js and pdf-lib are loaded with dynamic `import()` only when a file is opened / saved, so no other page loads them. `pdf-lib@1.17.1` (MIT) is the only added dependency.
- Coordinates: items live in "page space" (pdf.js viewport at scale 1 with the page's own /Rotate, top-left, y down). `geometry.ts` maps that to PDF user space with the page box (CropBox ∩ MediaBox) offset and /Rotate 0/90/180/270. A page turn added by the visitor is only an extra /Rotate, so items turn with the page.
- Output (since part B): the ORIGINAL document is edited in place with pdf-lib (`lib/pdf-editor/inplace.ts`), see "part B" below. Text uses the standard fonts when every character is WinAnsi and the bundled embedded fonts when one is chosen, otherwise it is drawn to a canvas and embedded as a PNG (with an invisible text layer for Arabic / Hindi). Highlights use Multiply blending.
- Honest limits (also in the page copy): "Edit text" covers the line and writes new text on top, so it is NOT secure redaction; Edit text reflows only inside the block you click (it never pushes neighbouring text); new text uses Helvetica / Times / Courier or a bundled font, not the original font file; scanned PDFs have no text to click until they are read; a protected PDF is saved WITHOUT its password; vertical or rotated-in-place text runs are not clickable. What the in-place save still drops is listed under part B.
- Pictures (`lib/pdf-editor/pictures.ts`, `picture-detect.ts`): found automatically per original page after its text is known (the page on screen first, then the others, one at a time; results cached like the text runs; nothing is uploaded). Real embedded images (normal PDFs): pdf.js operator list (`paintImageXObject` / inline / mask) with the current matrix mapped through `userToPageMatrix`, so /Rotate and CropBox are respected; images under 1 % of the page and a page-sized image are not offered. Picture-only pages (a full-page image, e.g. SlidesDone exports and scans): a photo finder on a rendered copy: 4 px tiles of a 480 px wide copy, "textured" = brightness varies (threshold adapts to the page's own noise), text lines (OCR or real text) are subtracted, thin lines are removed, components of at least 3 % of the page that are filled and plausibly shaped are kept, then every edge is snapped to the pixel where the flat background ends. Flat cards, gradients and shapes are not textured so they are not offered. Outlined in violet, dashed, labelled "Picture" (under the visitor's own items, over the page; text blocks stay on top). Click = pick up: the pixels are cropped from a render of the page at the picture's own resolution (1x to 3x, at most 4000 px a side / 12 million pixels; the bytes in the file are not extracted), rounded corners become see-through (flood from each corner over background-coloured pixels, accepted only when it is small and hollow like a corner), and a cover (`coverPatch`, filled smoothly from the colour around it; borrows the opposite side when the picture touches the page edge) is put under it. Both go to the bottom of the page's item list (so text the visitor already put on top stays on top). Result: an ordinary `image` item (move, corner-resize, delete, undo). Replace picture / Fit inside: the chosen picture is cut (cover) or letter-boxed (contain, see-through margin) to the item's box once, and the saved file holds exactly that; JPEG unless something is see-through (then PNG).
- Picture limits (measured on the generated fixtures and one real SlidesDone slide, see the suite checks O1-P3): a photo whose lower part is a flat dark band, a mostly flat photo (sky, studio backdrop), a photo that touches text, two photos side by side (merged or dropped), a photo on a busy pattern background, and photos smaller than about 6 % of the page side can be missed or have a wrong box; a rounded-corner photo is only made see-through when its corners can be told from the background; the moved picture of a rounded photo is a JPEG plus a soft mask (see "part A" below). Text on a photo is part of the picked-up pixels. Slanted images are not offered.

### PDF editor: picture side made production-ready (2026-11-12, part A)

Measured on the owner's real deck (13 slides, pictures only) and the generated fixtures. Checks: suite 62 `O2`, `O6` (owner files, skipped when `E2E_OWNER_PDF_DIR` is unset) and `S1`-`S6` (generated). Ground truth for the owner deck (visible words, photo boxes) is data in `e2e/lib/owner-deck-truth.mjs`; the PDF is never committed.

| | before (same pipeline, Node harness on the same 13 JPEGs) | after (real browser, suite O2) |
|---|---|---|
| photos found, IoU >= 0.9 | 5 of 6 (the dark photo of slide 12 missed), 0 false positives | 6 of 6 (IoU 0.997 to 1.000), 0 false positives |
| visible text items read | 95 of 105 (90.5 %) | 104 of 105 (99.0 %); the miss is "AI Notification Timing" read as "Al" (I / l look the same in that font) |
| junk readings | 4 (text inside the slide-9 photo) | 0 |
| cover left by a picked-up dark photo (dark fixture, vs the slide rendered WITHOUT the photo) | mean 8.6 / worst 65 levels | mean 0.7 / worst 1.0 |
| owner slide 12 cover | cover reached 2 px into the chevrons (below-photo pixels changed by up to 20.6, smear of chevron colour 64) | below-photo pixels unchanged (0.0), seam against the slide mean 0.7 / worst 1.4 |
| saved rounded photo | PNG with alpha (about +1.3 MB per picture) | JPEG 152 KB + 837 byte soft mask (0.55 % of the JPEG) |

- Photo finder (`picture-detect.ts` `findPhotos`): two independent cues merged. (1) the old texture cue. (2) the background MODEL: `fitBackground` fits a plane per colour channel to the pixels that are background (starts from the page rim, then keeps what the fit explains, text boxes never used); `deviationRegions` marks what differs from the model, closes and opens the mask (drops chevrons, rules, text remnants), and splits it into components; `photoLike` keeps a component only if its colours are continuous (>= 60 fine colour bins hold 90 % of its tiles) AND it has fine texture (>= 20 % of tiles vary), which is what separates a photo from a card, a panel, a gradient bar or a group of tiles (measured: cards 1-16 bins, the dark photo 178, bright photos 1000+). A texture region inside a model region is a fragment of the same photo and is dropped. `refineRect` picks the STRONGEST step edge near each side (not the first), measured on the biggest colour-channel change, and only snaps to the page border when no step edge exists (the cover slides have a 34 px margin). The "layout grid" idea was not needed.
- Cover (`cover.ts` `modelCover`): the fill is the background model evaluated over the box (flat colour if the model is flat there, else a small smooth PNG the viewer scales), validated against a ring just outside the box (falls back to the old pixel-ring method when the surroundings are mostly not background or the model is off there). A side with another shape right beyond the picture gets no padding (the owner's chevrons touch the photo's lower edge).
- Text finder passes (`ocr-core.ts`, pure, runs in the browser and in Node): (1) whole page, (2) flipped colours on dark pages, then `readUnexplained`: ink that no read line explains is found as SHAPES (flat colour areas: circles, chevrons, cards; pieces of one shape that a connector cuts apart are merged) and LOOSE ink (big numbers, small grey lines); each is cut out, turned into black-on-white by its OWN ground colour, rules / connector lines through it removed, enlarged until letters are about 34 px tall, and read with a page-segmentation mode that fits (one glyph = psm 10 with the digit alphabet first, a number = psm 7 digits first, a line = 7, a block = 6). Weak readings are believed only when the page confirms them: a number needs a sure number of about the same height (numbered list: "01" next to "02"), a label needs every word of 3+ letters to stand in a sure line ("Phase 1" next to "Phase 2"). Region passes only ADD lines (never replace). Text inside a photo is dropped unless it is big (>= 3.8 % of the page height) and sure (a title over a photo). About 4 extra reads per slide on the owner deck; 13 slides read in about 17 s in headless Chromium.
- Languages: a visible "Text language" list in the picture-page note (English, Spanish, French, German, Portuguese, Italian, Hindi, Arabic). Default: the visitor's last choice, else the document / site language (`<html lang>`), else English. Models are tessdata_fast (Apache-2.0, `LICENSE-tessdata_fast.txt` beside them), fetched ONLY when the language is chosen, same origin, kept in the browser's IndexedDB. Sizes as served (gzip): eng 1.97 MB, spa 1.13, fra 0.61, deu 0.85, por 1.00, ita 1.27, hin 0.92 (loads with eng), ara 0.72 (loads with eng); the six added models are 5.8 MB in the repo, `public/ocr` went from 13 MB to 19 MB. That is under the 12 MB mark, so ALL models are in the repo. `OCR_LANG_BASE` (env `NEXT_PUBLIC_OCR_LANG_BASE`, a full URL, no trailing slash) points the models at an asset host instead (CORS `Access-Control-Allow-Origin` for the site; `scripts/csp.mjs` adds its origin to `connect-src`); to move some or all out: upload `<code>.traineddata.gz` files to `<asset-bucket>/ocr/7.0.0/lang/`, set the variable, rebuild, then delete the files from `public/ocr/7.0.0/lang/` (keep eng). A model that cannot be fetched (offline, 404) gives a plain message with a retry button, the editor keeps working (drag a box), and English still reads (suite S5).
- Right-to-left: Arabic lines are found (logical word order is Tesseract's), the replacement text sits against the RIGHT edge of the found line and grows leftwards (`PdfEditorTool` `onRunPick` / `onText`, only for text that replaces a found line), the box and textarea are drawn right-to-left, and the saved file holds it as a picture of the text (`textToPng` already drew RTL): suite S4 measures the right edge in the saved page (1003.3 pt line end, 1000.4 pt ink end). Measured recall on generated slides (suite S3): Spanish 20/20 words, French 23/23, German 19/19, Portuguese 20/20, Italian 21/21, Hindi 20/21, Arabic 17/18. Arabic and Hindi lines can be split or mis-spelt more often (fast models): the visitor must check the words.
- Small files: a picked-up rounded photo is written as its JPEG plus an 8-bit `/SMask` (Flate-packed grey image) (`export.ts` `maskedJpeg`: pdf-lib's own JPEG embedder, extended by one dictionary entry, embedded immediately because pdf-lib only embeds the images it made itself at save). Colours under see-through pixels are replaced by the nearest solid colour (`images.ts` `splitAlpha`) so the JPEG has no hard step or halo. The picture shows on screen from a PNG blob that is never saved. Replace picture + "Fit inside" with a JPEG uses the same path; a PNG the visitor chose (a logo) stays a PNG (JPEG would ring around flat colour). Checked in pdf.js and in macOS `sips` (suite S6).
- (Superseded by part C: such photos are now offered as "Picture?" and close pairs are split.) Still not solved / honest limits: a photo that is mostly flat colour or nearly all black cannot be told from a card by statistics (the "drag a box to pick up a picture" tick covers it); two photos closer than about 13 px are merged; text finder: "I" and "l" are confused in some fonts ("AI" read as "Al"), rotated or curved text is not found, very small text on a big page may still be missed, Arabic / Hindi accuracy is limited by the fast models; the decorative connector lines inside a shape are removed only when they cross the whole cut-out. Document fidelity (forms, passwords, fonts, thumbnails, bold runs) is part B.

### PDF editor: document fidelity (2026-11-12, part B)

Checks: suite 62 `PB1`-`PB10` (generated fixtures from `e2e/lib/pdf-structure-fixtures.mjs` and `e2e/lib/pdf-encrypt.mjs`; `PB10` needs `E2E_OWNER_PDF_DIR`). New code: `lib/pdf-editor/{inplace,decrypt,forms,fonts,bullets,thumbs}.ts`, `components/free-tools/pdf-editor/{PasswordDialog,FormLayer,SaveOptions,BulletAsk,use-thumbs}`.

1. **Export in place** (`inplace.ts`, `export.ts`). The file is loaded with pdf-lib (`updateMetadata: false`, so Info, XMP and producer are not touched) and modified: untouched pages are the same page objects; an edited page gets its drawing APPENDED as content streams (original content wrapped in `q ... Q`, and in `/Artifact BMC ... EMC` for tagged files); its resource dictionaries are copied one level so nothing is added to resources other pages share; a page tree that changes (delete / move / duplicate / blank page) is rewritten as one flat `/Kids` list (inherited size, rotation and resources are first copied onto the pages); a duplicate is a new page object that shares the original's content streams. After that, everything pointing at pages is repaired and what nothing reaches any more is garbage-collected, so deleted pages are really gone from the bytes:
   - outline: an entry whose page was deleted is dropped (a parent that still has entries under it stays as a heading without a target); the others follow their page objects, so moved pages keep their bookmarks; `/Count` and `/First` `/Last` `/Prev` `/Next` are rebuilt. Named destinations (old `/Dests` dictionary and the name tree) pointing at deleted pages are removed; links (`/Dest`, GoTo `/A`, by array or by name) pointing at deleted pages are removed, links to kept pages need no change at all (they point at the page object); `/OpenAction`.
   - page labels (a number tree keyed by page INDEX) are rewritten as ranges over the new order (kept runs stay one range, `/St` is adjusted); a blank page gets an empty label.
   - form fields whose widgets all sat on deleted pages are removed; the safety net: whatever else (tagged structure, threads, ...) still reaches a deleted page is dropped from the catalog, and the check is made by walking the whole file.
   - pictures: producers like jsPDF list every picture in the resources all pages share, which keeps a deleted slide's picture reachable. Each kept page gets its own XObject list with only what its content draws (form XObjects followed), when pages were deleted.
   Measured on the owner's real files (suite PB10; those have no outline, form or labels): unedited save 5,986,876 -> 5,980,588 bytes (booking), 2,807,179 -> 2,803,257 (deck), 1,874,085 -> 1,864,280 (spec), object counts equal (spec 79 -> 78), 7 to 20 ms in Node; four pages deleted (suite PB10): booking 4,139,285 for 17 of 21 pages (-31 %), deck 1,892,135 for 9 of 13 slides (-33 %; the copy-pages export and a plain page-tree edit both left 2.80 MB because the pictures of deleted slides stayed reachable through shared resources), spec 1,858,285 for 25 of 29 pages. On the generated structured fixture (6 pages, 6 outline entries, named destinations, labels, XMP, optional content, tags, 5 fields, 3 links): editing one page keeps ALL of them (`PB1` compares outline, links, labels, fields, Info, named destinations, XMP, OCG, MarkInfo, Lang, PageMode with the original); deleting pages 2 and 4 and moving one gives the outline, labels and links computed in `PB2` and no trace of "Page 2" / "Page 4" in any content stream.
   **(Superseded by part C: the structure tree is pruned, duplicated pages keep fields and comments.) Dropped in part B:** tagged structure when a page is deleted (its tags would point into a missing page; kept when nothing is deleted); form fields and comments on a DUPLICATED page (two copies of one field would share a value; links are copied); outline / link / field entries that point at deleted pages; blank pages carry no tags or labels. **Not verified:** files with incremental updates and a corrupt xref (pdf-lib re-parses by scanning), hybrid object-stream files beyond the fixtures, PDF 2.0 `/AF` associated files, signatures (saving invalidates a digital signature, as any change does; the editor does not say so yet).
2. **Form filling** (`forms.ts`, `FormLayer.tsx`). Fields come from pdf.js annotations (text, multiline text, checkbox, radio group, dropdown, list box; signature fields and push buttons are not offered). They show as real controls over the page in Edit text, values live in `Doc.form` (undo / redo, one undo step per field) and are written with pdf-lib (`setText`, `check`, `select`, ...) followed by `updateFieldAppearances` with an embedded Helvetica, or `flatten` when the "Flatten the form when saving" box is ticked. Characters Helvetica cannot write become "?" in a field (no picture fallback in a field). The owner's three files have no form fields; the generated fixture (text, checkbox, dropdown, radio x2, second field on another page) is checked in `PB3`: values, appearance stream, outline kept, flattened file has no fields and the text is page text.
3. **Protected PDFs** (`decrypt.ts`, `PasswordDialog.tsx`, `SaveOptions.tsx`). pdf.js `onPassword` drives an accessible modal dialog (labelled, focus in the field and kept inside, Escape / Cancel back to the start, wrong password announced and asked again). pdf-lib cannot read or write encrypted files, so at save time a plain copy is made first by a decryptor written for this (`decrypt.ts`: MD5 + RC4 in 80 lines, AES and SHA-2 from WebCrypto): standard security handler V1 / V2 / V4 (RC4 40 and 128 bit, AES-128) and V5 revisions 5 and 6 (AES-256), user OR owner password, owner-password-only files (open with an empty password but restrict changes: detected, `ignoreEncryption` is NOT used because it would yield garbage). Re-encryption was not built: pdf-lib has no writer for it and nothing well-licensed and small exists in-browser; the saved copy is unprotected and the UI says so BEFORE download (a checkbox "I understand the saved copy has no password", Download stays off until ticked; owner-only files get the same note). Verified against files made by pypdf (independent: RC4-40, RC4-128, AES-128, AES-256 R5 and R6, user and owner passwords, owner-only, wrong password) and by the suite's own writer (`pdf-encrypt.mjs`: RC4-128 and AES-128, opened by pdf.js with the password too). Not supported: public-key security handlers and custom filters (message: cannot be saved), crypt filters other than Identity per stream.
4. **Thumbnails with edits** (`thumbs.ts`, `use-thumbs.ts`). The original page is drawn once per file page (224 px wide JPEG); a page with edits is composed from that picture plus its items (covers, pictures, shapes, pen lines, highlights, text in its fonts) after the page has been quiet for 250 ms, one page at a time, only pages whose item list changed (reference comparison); a result for items that changed meanwhile is dropped; one JPEG blob per page, revoked when replaced or when the page goes. Measured: the thumbnail shows an edit 240 ms after it, a 60-page file has 60 thumbnail pictures and 10 composed ones with no measurable heap growth (`performance.memory` 51.0 -> 51.0 MB), undo goes back to the plain picture at once.
5. **Bullets** (`bullets.ts`, `render.ts`, `BulletAsk.tsx`). Real text: the marker the run does not include is remembered with its box (`Run.marker`, for a marker apart from the words and for "• text" in one item). Picture pages: a small blob of ink in a strip left of the block's first line (`markerStrip` / `markerIn`: smaller than about a text size, not touching the strip's outer edge, clearly different from the background). UX: clearer than a hidden automatic step: when the words of a block are emptied, a small bar asks "Remove the bullet too? [Remove the bullet too] [Keep it]"; Remove adds one cover (one undo step) coloured from the ring around the symbol (or a smooth patch on a gradient). Measured in `PB6` (three real bullets: apart, apart, inside; removed, kept, removed, verified in the saved page's pixels) and `PB6b` (the deck's `<li>` disc: found as a 13 pt box, the saved slide has background there, the rest of the slide changed by under 40 levels). Not found: numbers like "1." are only found when they are about as small as a bullet; a marker more than 3.2 text sizes from the words.
6. **Mixed bold / italic** (`text.ts`, `render.ts`, `blocks.ts`, `AnnoView.tsx`, `export.ts`). `TextAnno.spans` = stretches [start, end) whose bold / italic differ from the item's own; real text runs now carry them (per piece of the line, then per line of a paragraph). `retext` lays out ONCE with per-stretch fonts and stores `lines` plus `sty` (one digit per character); the screen draws each stretch as a span (kerning and ligatures off), the PDF draws one `drawText` per stretch with the right font, advancing by that font's own width, the picture fallback draws the same stretches. Typing inside a stretch (or right after it) keeps its style, a whole replaced text takes the dominant style, and with words selected in the box Bold / Italic change only those (the buttons keep the focus and show the state of the selection). The "mixes bold" note now only appears when the styles could not be kept (text read from a picture). Measured (`PB7`): a stretch starts 0.72 pt from where the screen shows it (tolerance 1.2). Limit: while typing in a mixed line the caret is placed by the plain textarea (its glyph widths are those of one weight), so it can sit a few pixels off a bold stretch; what is drawn and saved is exact.
7. **Fonts** (`fonts.ts`, `public/pdf-fonts/`, `@pdf-lib/fontkit` 1.1.1 (MIT, pinned: the last release, pdf-lib needs a font parser for non-standard fonts)). Bundled, SIL OFL 1.1 (licence text beside the files): Inter, Plus Jakarta Sans, Roboto, Open Sans, Lora, JetBrains Mono, each regular / bold / italic / bold italic, Latin + Latin Extended, static TrueType made from the Google Fonts variable fonts (fontTools instancer + subsetter, hinting and layout features removed so the screen width is the PDF advance), 31 to 66 KB per file, 1.0 MB in all; `/pdf-fonts/*` is `public, max-age=31536000, immutable` (next.config.ts); nothing is fetched until a font is chosen or a line in that font is picked (`PB8` checks it). The screen loads the same file with `FontFace` before text is measured; the PDF embeds a SUBSET (`PB8`: Roboto edit + Open Sans line + one picture: +8,949 bytes), widths agree to 0.03 pt (164.44 pt in the file, 164.41 on screen). Auto-pick by font name (`closestFont`): names containing Jakarta, Inter, Roboto, Open Sans / Noto Sans / Segoe UI / Calibri / Verdana, Lora / Georgia / Cambria / Garamond, JetBrains / Consolas / Fira Code ... else Helvetica / Times / Courier by the old rule (OCR blocks keep that rule: their font is a guess from letter widths). The file's own embedded font is NOT reused: its subset rarely has the glyphs of new words, and re-embedding a font's licence-restricted file is not ours to do. A character the chosen font lacks makes that text a picture (as before).
8. **Arabic / Hindi text layer** (`export.ts` `hiddenText`). The picture stays (right shapes). Behind it: invisible text (render mode 3) in Noto Sans Arabic / Noto Sans Devanagari (subset files 138 and 182 KB, fetched only when such text is saved, embedded as subsets, shaping features switched off). Arabic (letters and spaces only) is one run, pdf.js gives back exactly the typed words; Devanagari and mixed Latin / Arabic lines are written character by character in typed order (a shaper would reorder vowel signs in the glyph stream and the copied text would come out wrong; checked with pdf.js: "नमस्ते दुनिया" and "English and مرحبا" come back exactly, `PB9`). `regenerator-runtime` 0.13.11 (MIT, 6 KB) is a dependency because fontkit's Indic shaper needs it. **Item 1 and 2 design (`picture-detect.ts`).** Non-local evidence, measured on the FULL-size copy (`regionEvidence`): (a) exact-colour count holding 90 % of the pixels (a fill: 1-2; a photo: dozens to thousands), (b) noise floor = median 8x8-block residual of the pixel against its 4 neighbours (flat fill and smooth gradient: 0 to 0.17; photo, even after JPEG: 0.27 and up), (c) planar residual of the block means (gradient = a plane). `verdict`: photo (noise >= 0.25) / "Picture?" (noise >= 0.2, or few colours that are not a plane and a sizeable text-free region of photo-like proportions) / synthetic. A second background-model pass at a low threshold finds the regions (a black photo on a near-black slide differs from the slide by only 14 levels). `splitMerged` cuts a region at a gutter found as a DIP in the background share of columns / rows (a 2 px gutter after JPEG is one or two columns that are only 30-100 % background; brightness counts fully, colour 40 %, because JPEG stores colour at half resolution). Tuned on the generated JPEG slides; the thresholds are statistics, not guarantees. "Picture?" is a dashed grey outline with its own label and explanation; one click picks it up like any picture.

**Item 3 design.** Model: `rot` (degrees clockwise on screen, about the box's TOP-LEFT corner, so text that grows along its own direction keeps its start) on `TextAnno`, `WhiteoutAnno` and `RunBox`; the box itself stays the unturned box, so wrapping, measuring and editing are unchanged. Real PDFs (`geometry.ts` `runFromItem`/`unturnRun`, `render.ts`): pdf.js text items whose matrix is a pure turn become runs in the text's own frame, are joined along their direction and then unturned; turned runs are never grouped into paragraphs. Picture pages (`ocr-core.ts` `readTurned`): `inkBlobs` joins unexplained ink in all directions; `textAngle` finds the angle whose projection profile is sharpest (sharpness, straightness, thickness), sideways text is read both ways (down and up) and the surer reading wins, the crop is turned upright (`turnCrop`), read as a line, and the box is mapped back with the turn. A rule or a connector (thickness < 8 px) is skipped; at most 14 candidates per page; curved or irregular ink (middle line wanders by more than 0.6 text heights) is counted (`OcrNotes.curved`), its surroundings are not read (no junk), and the page says "N curved text areas were not read: drag a box over them".
